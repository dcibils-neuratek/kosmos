# JetSki W7: a browser to use every day

Written 14 November 2026, the day Diego made it the work: "Let's finish the
browser now end to end which is the most importante part of the os now for
a daily driver usage". `webkit.md` is the design and `webkit.html` the
window, both agreed on 11 November. This file is the order W7 and W8 are
built in, step by step, and what each step's test is.

## The order: the processes first

`webkit.md`'s order holds. Diego confirmed it on the same day, choosing it
over a browser in one process. The reason is in WebKit's source: the curl
loader that ran inside a page's process (`ResourceHandleCurl`, for
WebKitLegacy) has been removed upstream. Today's curl loader is
`NetworkDataTaskCurl`, and it lives in WebKit2's network process. A browser
in one process would need a loader of our own, a second copy of that one,
thrown away when the processes arrive. So:

1. **W7a, the three processes.**
2. **W7b, pages from the network**, through WebKit's own loader.
3. **W7c, the window.**
4. **W7d, what a day of browsing needs.**

## W7a: the three processes

WebKit2 (`ENABLE_WEBKIT`). The UI process is JetSki itself. Each tab has a
web process running WebCore and JavaScriptCore. One network process runs
curl.

- **`IPC::Connection` on Nebula's endpoints.** A message is a call or a
  pulse, and anything larger is a region whose handle travels with it
  (*Control by message, data by shared memory*). A port's connection is
  `Platform/IPC/<port>/ConnectionPort.cpp`; Kosmos's is written for
  endpoints.
- **The process launcher** on `SYS_SPAWN`, with a role, one image
  (`jetski.elf`) started three ways. Each process gets only the
  capabilities its role needs: the network process the Network Kit, a web
  process none of the disk.
- **A read-only region in Nebula**: WebKit's `SharedMemory` hands out
  read-only views. *Built*: `SYS_MEM_READONLY` makes a second capability
  to a region that may only be read. It maps without write access and is
  never executable, it stays read-only when it is passed on, and a
  sandbox's guest refuses it (`testing.md` 18.805).
- **Test, `x86-webkit2`**: WebKit's own MiniBrowser shape, headless. The
  UI process starts a web process and a network process and loads a
  recorded page; its picture, read back through a region, must be the one
  W6 paints. The control is a web process ended halfway through: the UI
  process must say so, and load the page again in a new one. *Built*
  (`testing.md` 18.806): W6c's two pages, each painted pixel for pixel as
  GTK's port paints it, and the page loaded again in a new web process
  after its first was ended at the commit; 2.1 s in the guest.

### What W7a is made of, as built

- **The processes are one image in three roles.** `SYS_SPAWN` starts a
  child from the image its parent was made from, so a web process is
  `jetski.elf` - or the suite's image - again, in role 500, and the
  network process in 501 (`KosmosLaunch.h`). `user/init/main.c` sends
  roles 500 to 515 to the image's `kosmos_project_role`, after the C++
  constructors.
- **A child is handed its connection and what its role may reach**, by
  index from 0: the connection's region and two endpoints, a launch page,
  then each mount it may see, the network, and the console. A web process
  gets every mount but `/Home`, and no network; the network process gets
  everything. Nebula has no command lines, so the identifier WebKit gave the
  process travels in the page.
- **A process with no Lua side is heard through a console it is handed.**
  The POSIX layer's standard output and error go to the console's endpoint
  (`posix_console`) when `SYS_WRITE` refuses them. Before that, a web
  process said nothing at all, its crash included.
- **No compositing.** The web process paints on the processor into the
  `UpdateInfo` bitmaps of WebKit's non-composited drawing area, which the UI
  process's `BackingStoreSkia` keeps; `WKPagePaintKosmos` paints the last
  picture into pixels with a pitch. The view, its page client and `WKView`
  are PlayStation's, which without a WPE backend are nothing of
  PlayStation's.
- **The user agent** is GTK's shape with Kosmos's name: `Mozilla/5.0 (X11;
  Kosmos x86_64) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/60.5
  Safari/605.1.15`. WebKit's per-site quirks arrive with W7d.
- **The first bug was the handshake's order.** The maker ended the endpoint
  the other side's first call came in on before answering it, and ending an
  endpoint abandons every call still waiting on it - that one too. The
  answer goes first now.

### How a connection is made of Nebula's parts

A Nebula message is 2,048 bytes with one capability out of band, and a
call waits for its reply. WebKit's `IPC::Connection` sends in both
directions at once, without waiting, messages of any size, each with any
number of attachments: regions, other connections, semaphores. So a
connection is built from three of Nebula's parts, and Kosmos's file is
`Platform/IPC/kosmos/ConnectionKosmos.cpp`, beside Unix's:

- **Two rings in one region**, one for each direction, single producer and
  single consumer with indices, as the audio rings are. A message is
  encoded straight into the ring. One larger than a quarter of the ring
  goes in a region of its own, which travels as an attachment, and the
  ring carries only that.
- **A pulse to say there is more.** The sender pulses the receiver's
  endpoint only when the ring was empty before it wrote. A receiver that is
  busy reading finds the next message without being told.
- **An attachment is a capability, sent first.** For each one, the sending
  thread calls the receiver's endpoint with it. The receiver's connection
  thread queues it and replies at once, so the call waits only for the
  kernel's copy. Then the message goes into the ring, saying how many
  attachments it has. The calls come before the message that names them,
  from the same thread, so the attachments are always waiting when the
  message is read.
- **Each side receives on an endpoint the other side made.** An endpoint
  goes with the process that made it, and everything waiting on it wakes
  with an error (`kernel/ipc.c`, `ipc_endpoints_release`). So a side whose
  peer ends learns it at once, from the receive it is already blocked in,
  with nothing polled. `createConnectionIdentifierPair` makes everything
  in one process, so the other side's first act, from its receiving thread,
  is a call handing the maker a new endpoint of its own, and the maker
  receives on that from then on. Only that side's receiving thread ever
  calls, and only once, before it receives; the maker's never calls, so two
  receiving threads can never wait on each other. A side that closes
  destroys the endpoint it made, and the other side sees the same error a
  crash gives.
- **A ring that is full is waited for, not polled.** The sender calls the
  receiver with nothing attached; the receiving thread empties the ring
  into WebKit's queue, which it always can, and then answers.
- **A connection's identifier** is the two endpoints, the ring's region,
  and which side it is: three capabilities, handed to a new process at
  `SYS_SPAWN`, or sent one at a time down a connection that already
  exists. Each is held as a `KosmosCapability`, WTF's counted capability,
  which an attachment is too.
- **`IPC::Semaphore`** is an endpoint: signal is a pulse, and wait is a
  receive with a deadline. A futex cannot cross a process.
- **Held by WebKit's own tests**: `TestWebKitAPI`'s `ConnectionTests`
  (41), `ArgumentCoderTests` and `EventTests`, built for Kosmos and run in
  the guest. The control is a ring whose index is advanced one message
  early: the tests must fail.

## W7b: pages from the network

The network process's `NetworkDataTaskCurl`, as WebKit ships it, over the
POSIX layer's sockets on the Network Kit:

- HTTPS on OpenSSL, with Mozilla's roots as
  `/Kosmos/Settings/ssl/cert.pem`. `br`, gzip and deflate decoded.
- Cookies in curl's `CookieJarDB` on SQLite, in
  `/Home/Settings/JetSki/cookies.db` - named by JetSki's data store, since
  WebKit names a cookie file only on Cocoa (built 0.11.418, `testing.md`
  18.813).
- The HTTP cache, WebKit's own, on disk.
- Nothing waits: the network process answers on its own threads, and a
  web process never blocks on it (*Nothing waits on hardware*).
- **Test, `x86-sites`**: the recorded sites served over HTTP and HTTPS by
  a server on this Mac, and loaded by URL. Each must paint as it does from
  files. The control is the server answering 404 for one style sheet, and
  the picture must differ. Then the live sites on the M700, outside the
  gate.

### W7b as built so far

**HTTP works end to end** (`testing.md` 18.807): the network process
fetches a page and every font and picture it names, by WebKit's own loader
on curl, and the web process paints them. `x86-sites` holds WebKit's WOFF2
and AVIF reference tests to their references, each loaded by URL from a
server on this Mac.

What it needed outside WebKit is POSIX-shaped and stays inside the process:
**a pipe** (`runtime/posix/pipe.c`), because curl's scheduler sleeps in
`poll` with no deadline and is woken by a byte down one. A `poll` on a pipe
and sockets together waits in the network stack, so a pipe's change also
nudges the stack (`NET_OP_NUDGE`) to look again at a wake entry the client
writes (`NET_WANT_WAKE`). Inside WebKit, one fix, patch 0023:
`RedBlackTree::remove` now resets the node it removes, whose stale
`CheckedPtr` links crashed the UI process on the second page.

**HTTPS works** (`testing.md` 18.808). curl trusts Mozilla's roots, built
into the image from `assets/ca/cacert.pem` - the same file the TLS Kit's
anchors come from, so the browser and the rest of Kosmos trust the same
authorities - and every `.pem` a person puts in
`/Home/Settings/JetSki/Certificates/`, which is how a server of one's own
is trusted. (This document planned `/Kosmos/Settings/ssl/cert.pem`, a
second copy of the bundle in the image; one file, compiled in, is one copy
fewer.) `example.com` loads from the internet in QEMU.

Still to come in W7b: cookies, the disk cache, and the live sites on the
M700.

## W7c: the window

`jetski.elf`, an installed application (`docs/elf.md` step 5), opens the
window `webkit.html` drew: tabs in the window's band and an address field.

- **Painting**: each web process paints into a region, and the UI process
  hands it to the window manager as the window's surface. Tiles and the GPU
  come from the *Fast* section and are measured after.
- **Input**: keys with text input, the pointer and its cursor shapes, the
  wheel and scrolling, selection, and copy and paste through the window
  manager's clipboard.
- **The address field**: a URL, or words searched for.
- **Test, `x86-jetski`**: the window driven by the display harness. Open a
  recorded site, scroll, click a link, type into a search field, go back,
  and copy text out. Each is checked against the screen.

### The first slice: a page in a window

Diego, 14 November: "window then jit", and "i want to see the actual
browser running". So W7c starts with the smallest thing that is a browser
on screen, and grows from it:

1. **`jetski.elf`**, the UI process as a kit, as `webkit2test.elf` is one:
   a view of a size, `load(address)`, `pump(ms)` - WebKit's run loop for at
   most that long, returning what happened (title, address, progress, a
   new picture) - and the picture painted into the window's surface.
2. **`JetSki`, the application**, in `/Home/Apps/JetSki`: a `ui.lua`
   window with the address field above the page, Enter to load, and the
   page drawn below as `webkit.html` draws it.
3. **Words**: the web process given `/Kosmos/Fonts`, so pages have text
   (the test harness's pages have none, `testing.md` 18.808).
4. **The pointer and the wheel**: clicks on links, and scrolling.
5. **Keys** into the page, and the rest of the list above.

The first picture of it is shown to Diego as soon as step 3 paints.


**Built, 14 November (0.11.415, `testing.md` 18.810)**: steps 1 to 3 -
`jetski.elf` with `open`, `load`, `back`, `forward`, `reload`, `stop`,

`/Home/Apps/JetSki`, an address or words (`browserprefs.destination`, the

**Input, 14 November (0.11.416, `testing.md` 18.811)**: step 4 and

through patch 0024 and `WKPageKosmos`, and `WebPageKosmos.cpp`'s editing
commands. Then (0.11.417, 18.812) `position: fixed`, transforms and

pointer's shape, the right button's menu; Google answers with its robot

## W7d: what a day of browsing needs

- Tabs: open, close, and switch with keys.
- Back and forward, history, and the address field completing from them.
- Bookmarks, as files in `/Home`.
- Downloads into `/Home/Downloads`, shown as they arrive.
- Find in page, zoom, and printing to PDF through the PDF Kit.
- The session restored after any stop: every window and tab.
- A page that says why a certificate was refused.
- HTTP/2, with nghttp2 held to its own tests.
- A tab whose web process ended shows a page saying so, with Reload.
