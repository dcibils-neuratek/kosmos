# W6 - WebCore draws a page

JetSki's sixth step (`docs/webkit.md`): WebCore, headless, laying out a
page and painting it with W5e's Skia into a region - the first time a web
page is drawn by WebKit on Kosmos. Written 13 November 2026, the day W5
finished, before any of it is built; both decisions taken by Diego the
same day (*Decided*, at the end).

**What W5 left.** JavaScriptCore runs (W4). Every library WebCore links is
built and held to its own tests: pictures, FreeType and HarfBuzz, SQLite,
libxml2, libpsl, OpenSSL, curl, and Skia drawing every pixel as on this
Mac (`docs/w5.md`).

---

## What W6 is

**A page from a file, laid out and painted, with no window and no
WebKit2.** W7 is where the three processes and the window arrive. Here the
whole of the engine is one program in the guest:

1. **A Kosmos port of WebCore**, `PORT=Kosmos` in WebKit's CMake beside
   `JSCOnly`: WebCore and its platform layer - Skia for graphics, FreeType
   and HarfBuzz for text, the W5a decoders for pictures, curl for the
   network, SQLite for storage, libxml2 for XSLT - with what Kosmos has
   not got turned off (GStreamer, WebGL, WebRTC, accessibility, the
   sandbox, GLib). Kosmos files where WebCore asks the operating system
   something: the clock, threads' run loop on `RunLoopGeneric`, memory
   pressure, the fonts' folder.
2. **A page with empty clients.** WebCore can make a `Page` without
   WebKit2: `SVGImage` does it for every SVG picture, with
   `pageConfigurationWithEmptyClients`. The harness does the same with
   clients of its own where an empty one would not do - a loader strategy
   that reads `/Home` and serves the recorded sites - loads the page, runs
   its scripts and timers to quiescence, lays it out and paints it into a
   Skia surface over a region.
3. **What it says**: the render tree as WebKit's own tests print it
   (`externalRepresentation`, what `DumpRenderTree` prints), a fingerprint
   of the picture, and the load, layout and paint times.

**Size.** Measured at the end of W5: JavaScriptCore's objects for x86-64
are 44 MB and Skia's 20 MB, built without debug information. WebCore has
4,432 source files to JavaScriptCore's 1,329, and generates its DOM
bindings, so its objects should be some hundreds of megabytes, a gigabyte
or two at most. 9.9 GB are free. **It fits**, which `webkit.md` and
`w5.md` had doubted.

## Decisions for Diego

### 1. The source: WebKitGTK's tarball lacks the curl backend

`tools/upstream.py` fetches the WebKitGTK 2.54.2 release, and W4 and W5
were built from it. **It ships only GTK's platform files**: WebCore's
network code is libsoup's (`platform/network/soup`, on GLib), with
PlayStation's two curl files but not `platform/network/curl` itself; no
`NetworkProcess/curl` in WebKit2; no PlayStation, WPE or Windows options in
`Source/cmake`; and no `LayoutTests`. JetSki's design is WebKit on curl,
the PlayStation port's choice, GLib-free.

WebKit's git has a tag for the release, `webkitgtk-2.54.2`, at commit
`b95c91b1c0ee43cc86d25ff7af73038f67a88e04`: the same source the tarball
was cut from, with everything.

- **A. The tarball, and what it lacks from git at the tag's commit**
  (recommended). A sparse, blob-filtered fetch of that one commit, only
  the directories the tarball does not carry - curl's in WebCore and in
  WebKit2, PlayStation's options and platform files where the Kosmos port
  follows them, and the `LayoutTests` W6 is held to - overlaid on the
  tarball's copy, the commit held as libpng's and libwebp's are. Some
  megabytes of source, and some hundreds for the tests chosen. W4 and W5
  are unchanged.
- **B. WebKit's git at the tag, whole**, sparse to `Source/`, `Tools/`
  and the chosen tests, in place of the tarball. One source rather than
  two, at the price of every W4 and W5 build moving onto it and being
  proven again. The full tree with all of `LayoutTests` is several
  gigabytes; sparse, about a gigabyte.
- **C. libsoup, as GTK does.** No new fetch, but GLib and libsoup in the
  process, which the design chose WebKit's PlayStation shape to avoid.

### 2. What a page is held to

`webkit.md` said "compared with one Safari's engine draws on this Mac".
Safari draws with CoreGraphics and CoreText, Kosmos with Skia and
FreeType: every glyph's edge differs, so a picture cannot match exactly,
and a tolerance wide enough for text is wide enough to miss a bug.

- **A. WebKit's own LayoutTests, as text** (recommended). WebKit holds
  itself to tens of thousands of tests whose expected result is text - the
  render tree's boxes and positions, or what the page's script printed -
  much of it the same on every port. A chosen subset, run headless in the
  guest by the harness, each held to its `-expected.txt`, as test262 and
  HarfBuzz's suite are; the count kept as a regression, the failures
  named. **And the pictures** of the recorded sites (`webkit.md`,
  *Testing*) compared with Safari's with a tolerance and looked at by a
  person, as a report rather than a gate.
- **B. The same Kosmos WebCore built for this Mac, under Rosetta**, as
  Skia's reference is, and every pixel held to it. Exact, but it means
  porting WebCore to macOS as a Unix-like system first: the WTF Mac build
  already wanted files the tarball lacks, and it is weeks of work that
  proves the port agrees with itself rather than with WebKit.
- **C. Safari's pictures, with a tolerance**, as the gate. Quick to set
  up, and weak, for the reason above.

## W6a - the source and the port

**The overlay.** `tools/upstream.py`'s `WEBKIT_OVERLAY` names WebKit's git,
the commit `b95c91b1c0ee43cc86d25ff7af73038f67a88e04` and five patterns:
curl's directories anywhere under `Source/`, PlayStation's and WPE's
options, and their platform files. `upstream.webkit_overlay()` checks it out
sparse (`--no-cone`) and blob-filtered, one commit deep, into
`build/upstream/webkit-overlay`, refusing any other commit as every
checkout there does. `webkit_build.py` lays it over its copy of the release
before the patches: **89 files**, 47 of them WebCore's curl backend, and not
one the release has - a file both carry must be the same bytes, or the
build stops, which is what says the two were cut from the same source. The
LayoutTests join the patterns at W6c, when the subset is chosen.

**The port.** `PORT=Kosmos` (`runtime/cxx/jsc.cmake`), in place of JSCOnly:

- `0013-a-port-named-kosmos.patch`: Kosmos in WebKitCommon's list of ports;
  `BUILDING_KOSMOS__` giving `PLATFORM(KOSMOS)` and `BPLATFORM(KOSMOS)`;
  and no Apple SDK looked for on this Mac - WebKit looks before anything
  else whatever it builds for, and JSCOnly's build had found the macOS
  one and never used it.
- `runtime/ports/webkit/Source/cmake/OptionsKosmos.cmake`: the port's
  options. JSCOnly's for now, with WebCore off until W6b.
- `runtime/ports/webkit/Source/WTF/wtf/PlatformKosmos.cmake`: WTF's sources
  for this one system, where JSCOnly's file chose among Windows, Darwin,
  Linux and FreeBSD; it names `SignalsKosmos.cpp` and
  `MemoryFootprintKosmos.cpp`, so 0002 lost its hunk naming one and 0005,
  which only named the other, is gone.

**Held to being the same engine.** JSCOnly configured beside it into a
scratch directory: `cmakeconfig.h` differs in nothing a source reads - three
options only JSCOnly declares, which read as off either way, and the API
tests, which JSCOnly forces on and nothing builds - and a WTF file's flags
differ only in `-DBUILDING_KOSMOS__=1`. A first draft also took
PlayStation's `USE_ISO_MALLOC OFF`, which that comparison caught and which
went: W6a changes the port, not the engine.

**And what uses WebKit's headers says which port it is.** The Makefile
compiles `wtftest.cpp` and `jsc_kosmos.cpp` with WebKit's `cmakeconfig.h`,
and had never given them a port's define - harmless while JSCOnly defined
no `PLATFORM()`, and under Kosmos a library built with `PLATFORM(KOSMOS)`
and callers built without it. `WEBKIT_USER_FLAGS` is now the one place
those flags are, the port's define among them, and `x86-wtf` holds it:
`wtf port=kosmos` leads the line. Control, `make test ONLY=x86-wtf
WEBKIT_PORT_DEFINE=` - `port=none`, and the suite fails.

## W6b - a decision for Diego: WebCore without a GPU

**What W6b found.** With `ENABLE_WEBCORE` on, every library WebCore asks
for is found where W5 built it - curl, OpenSSL, HarfBuzz and its ICU
library (0.11.397), libxml2, libwebp, libpng, libjpeg-turbo, SQLite,
libpsl - and configuring stops at one line: WebCore links OpenGL ES on
every port (`WebCore/CMakeLists.txt`, ANGLE, libepoxy or the system's GL).
Every port WebKit has stands on a GPU API. WebKit's Skia code reaches it
in fifteen files - its painting engine, its accelerated image buffers,
its compositing layers - and chooses at run time: with no GPU display it
paints on the processor, which is how WebKitGTK runs on a machine with no
GPU. Skia itself already has its GL backend compiled (`SK_GL`,
`SK_GANESH`, W5e); it has no way to reach a GPU.

Kosmos has no GL ES. The GL Kit is TinyGL, OpenGL 1.1 with a fixed
pipeline, and Skia's GPU code needs GL ES 2 or later.

- **A. An EGL with no display** (recommended). The Khronos headers
  WebKit already carries (`Source/ThirdParty/ANGLE/include`), and a small
  Kosmos library behind them: `eglGetDisplay` says there is none, so
  WebKit takes its processor path, and each GL ES function stops the
  process loudly if it is ever reached, since with no display no context
  can exist to call it on. WebKit is not patched for it. When Kosmos has
  a GPU API - virgl under QEMU, the M700's own (`m700-gpu.md`) - that
  library is what gets a real implementation, and WebKit, Skia and every
  other program that wants GL ES gain it without changing.
- **B. WebCore patched to build with no GL at all** under Skia: about
  fifteen files, a patch set that grows with every WebKit release and is
  undone when a GPU arrives.
- **C. A real GL ES on the processor now**: Mesa's softpipe. llvmpipe, the
  fast one, compiles shaders with LLVM at run time - a JIT, which Kosmos
  does not allow (`docs/w4.md`). softpipe interprets, and is slow, and
  porting Mesa is weeks of work. It would give WebGL and GPU compositing,
  slowly.

**Decided by Diego, 13 November 2026: A, an EGL with no display.** WebKit
unpatched for it, painting on the processor; the library is the door a
GPU API later fills.

## W6b - WebCore on Kosmos, laying out WebKit's own tests

**Built, 0.11.398.** WebCore compiles as WebKit's Kosmos port and links
into `webcoretest.elf`, a harness in the shape of WebKit's own
`testing/TestPage.cpp`: a `Page` with empty clients, a frame view of 800
by 600, a page written into its document, layout, and the render tree as
text (`externalRepresentation`). The suite `x86-webcore`
(`tools/run_webcore.py`) gives it fourteen of CSS 2.1's LayoutTests -
`abspos-containing-block-initial-004a` to `-009f`, how a positioned box
finds the initial containing block - fetched from WebKit's git at the
tag's commit with Ahem, the font LayoutTests are measured in, and holds
every line of each tree to the test's `-expected.txt` - the generic one.
A port overrides one under `LayoutTests/platform/` where its tree
differs, and at this commit none overrides these fourteen as text (GTK's
folder has their pictures, which are W6c's). **All fourteen match**, in 1.4 s in the guest. Control:
`KOSMOS_WEBCORE_BREAK=page` moves one box a pixel and the suite names
the test and the lines.

**What the port is made of.** Most of it is other ports' files, used as
they are and listed in `PlatformKosmos.cmake`: curl and OpenSSL as
PlayStation takes them, Skia and HarfBuzz as WPE does, Adwaita's theme
(GTK's and WPE's form controls and scroll bars, drawn with no toolkit),
TextureMapper built and never run, and PlayStation's screen, system
fonts, MIME types and network notifier. Kosmos's own, in
`platform/kosmos/`:

- **`SharedMemoryKosmos.cpp`, `KosmosRegion.h`**: WebKit's shared memory
  as Nebula regions - a handle is one capability, held by a reference
  count, dropped when the last copy goes. Protection is not enforced:
  Nebula has no read-only mapping yet, which W7 needs before a region
  crosses to another process (roadmap).
- **`FontFolderKosmos`**: the folder Skia's directory manager reads
  fonts from, `/Kosmos/Fonts/` unless a program says otherwise - the
  harness points it at the test's own.
- **`AXObjectCacheKosmos.cpp`**: accessibility with no service to tell,
  as Haiku's and PlayStation's ports have it.
- **`PasteboardKosmos.cpp`, `EditorKosmos.cpp`**: a pasteboard that holds
  nothing, until it is the window manager's clipboard (W7).
- **`PlatformKeyboardEventKosmos.cpp`**: a key down sorted from the
  character it typed, as GTK's is.
- **`CurlSSLHandleKosmos.cpp`**: curl's TLS on its defaults; the roots
  Kosmos trusts are handed over when JetSki fetches its first page.

And six patches (0014 to 0019), each a guard that names Kosmos where a
port with the same need is already named, except 0016: WebCore's OpenSSL
code reaches into structures OpenSSL 4 has made opaque, and goes through
their accessors instead.

**Two names GL ES and GL 1.1 share.** TinyGL, the GL Kit, is in every
Kosmos image, and twenty of GL ES's functions - `glEnable`, `glViewport`
and the rest - are its already. The EGL Kit's stubs leave those to it,
by what `nm` says TinyGL's objects define: 338 stop the process with
their name, and the twenty, with no TinyGL context, reach a null one and
fault. None is reached: Skia asks for GL only through a display, and
there is none.

**What the harness supplies, and a browser will.** A page asks the
program that made it for its *strategies* - how to load, play media and
hold blobs. WebKit's web process and WebKitLegacy each bring theirs and
neither is in this source, so the harness's load nothing: its pages
arrive through the document's writer. The real loader - curl through
WebCore's `ResourceHandle`, as WebKitLegacy's does it - is W6d's.

**What the system gained on the way**, each in the gate:
`struct bus_device`'s `class` is `class_code` (C++ cannot read the
other; `kernel/syscall.h`), six more of musl's maths functions,
`__cxa_thread_atexit` (a thread's `thread_local` objects destroyed as it
ends, newest first and before its keys' - the POSIX suite checks the
order), and the kit named in `sys_user.c`'s table of image kits.

Next, W6c: the page painted - Skia into a region - and the LayoutTests
subset widened.

## W6c - the page painted

**Painting built, 0.11.399.** The harness's second door,
`webcoretest_paint`, wraps a Kosmos surface's pixels - `gfx`'s own
0xAARRGGBB, which is Skia's `kBGRA_8888` - in an `SkSurface` without
copying them, brings the page's style and layout up to date, and has the
frame view paint into a `GraphicsContextSkia` on the processor. The Lua
side is one call, `kit.paint(folder, page, surface)`, and the picture is
saved with `gfx.encode_png` - the PNG writer every screenshot uses, so
nothing new encodes.

`x86-webcore` paints each of its fourteen pages at 800 by 600, brings the
pictures back off the disk to `build/webcore/pictures/`, and holds each
**pixel for pixel to GTK's `-expected.png`** of the same test
(`tools/pngread.py` reads them). The two are drawn by the same Skia, and
these pages have no text, so there is nothing a font engine could make
differ. **All fourteen are identical, 480,000 of 480,000 pixels.**
Control: `KOSMOS_WEBCORE_BREAK=picture` changes one pixel of the first
expected picture, and the suite names it - (400,300), GTK `00ff00`,
Kosmos `ffff00`.

This goes past 2A, which holds pages to text: it holds these fourteen
to pictures too, because here a picture can be exact. A page with text
cannot be, since GTK draws glyphs through FreeType and fontconfig, and
those pages go back to text only.

**Text, 0.11.400.** Twenty-five more LayoutTests, with text in Ahem:
every test at the commit whose render tree is one file for every port,
whose page names Ahem by family, and which needs nothing loaded or run
(no script, picture, style sheet, web font or form control) - ruby,
tables with collapsed borders, bidi, soft hyphens, white space
(`upstream.WEBKIT_TEXT_TESTS`). Ahem's glyphs are squares of the em, so
their trees measure the same everywhere. One of the twenty-six found is
left out: `emphasis-overlap` lays out a space in the default font, which
on every port's test fonts is a serif with Times's metrics. **All 39
trees match** (and the fourteen pictures still do). Control:
`KOSMOS_WEBCORE_BREAK=text` sets `soft-hyphen-3`'s Ahem a pixel larger.

They found four things, three of them in how the harness runs a test:

- **Font families in any case.** CSS ignores a family's case, and so
  does WebKit's cache of what a family found - "ahem" and "Ahem" are one
  entry. Skia's manager for a folder does not, so a page asking for
  `ahem` found nothing, and that nothing was kept for every later
  "Ahem" at the same size: one lowercase page emptied the text of the
  pages after it, which is why the failures moved with the order.
  Fontconfig matches without case for the other ports; Kosmos's port
  now spells the name as the folder does first (patch 0020,
  `kosmosFontFamily` in `FontFolderKosmos`).
- **Whole-pixel advances.** WebKitTestRunner's web process calls
  `FontRenderOptions::disableHintingForTesting()`, which turns subpixel
  positioning off, so Skia rounds every advance. Without it FreeType's
  16.16 scale showed through: Ahem at 25 pixels advanced 25.0001, and a
  run of them came out a pixel wider. The harness calls it too.
- **Scroll bars of fifteen pixels.** `run-webkit-tests` turns on mock
  scroll bars, the same on every port; the Adwaita theme's overlay ones
  took nothing from a page wider than the view, which was 15 pixels
  taller than expected. The harness turns them on.
- **A page's bytes through WebCore's decoder.** The harness made a string
  of a file itself, so a byte-order mark became a character. Pages are
  now decoded by `TextResourceDecoder`, as a loaded page's bytes are.

**Generic families, 0.11.401.** `serif`, `sans-serif` and `monospace`
named nothing in a folder, so text in the default font - most text on
the web - had no font and measured nothing. Fontconfig decides them for
the other ports; on Kosmos `kosmosFontFamily` does, with the case: serif
(and `ui-serif`, `cursive`, and the standard family a page with no font
is in) is IBM Plex Serif, sans-serif (`system-ui`, `ui-sans-serif`,
`fantasy`) IBM Plex Sans, monospace (`ui-monospace`) IBM Plex Mono.
`x86-webcore` holds a page in each generic family, and one in none, to
the same page naming the face: identical trees, with the text measured.
Control `=generic` names Plex Sans beside `serif`. The default font's
page, painted, is the first text WebKit drew on Kosmos.

The faces are the harness's folder's. On the desktop, Kosmos's fonts are
built into its image, and `/Kosmos/Fonts/` - WebCore's folder by default
- does not exist yet: W7 gives the browser its fonts as files.

Still W6c's after that: pictures inside a page, which need the loader
(W6d).

## W6d - scripts, and a page's files

**Built, 0.11.402.** A page now runs as a loaded page does: its scripts
run, its files are fetched, and it is laid out after its load event, as
WebKitTestRunner dumps it then.

- **Scripts run.** A page made with empty clients is given an SVG
  picture's frame - sandboxed in every way, scripts included - so the
  harness clears the main frame's sandbox flags, and turns scripting on.
- **A page's bytes go in as a loaded page's** (`DocumentWriter::begin`,
  then `addData`), not `document.write`'s way, where a script does not
  run as it is met. The parser decodes them, so `TextResourceDecoder`
  went from the harness again.
- **Its files come from `/Home`** through `FileLoader`, the harness's
  `LoaderStrategy`: a file URL's bytes, answered on the main run loop as
  a network process's answers arrive - the response, the bytes, the end,
  each a turn of the loop after the request. Anything that is not a file
  is refused. A browser's loader is the network process's, at W7.
- **Then the run loop, until the load event has been** - what the page's
  scripts, files and timers did by then is the page.
- **Pictures are fetched as they are met** (`loadsImagesAutomatically`,
  as WebKitTestRunner sets it; empty clients' pages leave it off).
- **And the scroll position after the tree**, which WebKitTestRunner
  writes and WebCore does not: `scrolled to x,y` when the window's offset
  is not nought.

Thirty-seven more LayoutTests, every one at the commit whose tree is one
file for every port and whose page needs only a script or a picture beside
it (`upstream.WEBKIT_SCRIPT_TESTS`): floats, positioning, tables, ruby,
generated content, text whose DOM a script changes. **All 76 trees
match**, and the fourteen pictures and four generic families still do.
Controls: `=script` takes `rtl-fixed-positioning`'s one script out, and
its tree loses `scrolled to -100,100`; `=image` leaves
`show-shoes-vs-pie.png` off the disk, and the three pages that load it
lay out a picture of nothing - without the process dying.

**It found one bug in Kosmos, and it was in the POSIX layer.** The three
pages with a picture ended the process, code 70, with nothing said.
WebCore asks `inet_pton(AF_INET6, host)` of every URL's host before it
asks `AF_INET` (`isIPAddressDisallowed`, before every request), and takes
any answer but nought for yes. Kosmos's answered -1 - no such family -
so every host, a file URL's empty one included, "was" an IPv6 address
made of whatever the stack held; when those sixteen bytes were all zero
the request was refused as an address of zeros, and the refusal's path
asked a `std::optional` for a value it did not have. That is why a trace
in `CachedResourceLoader` made the crash go away: it changed what was on
the stack. `runtime/posix/inet.c` now reads and writes IPv6's text forms
(RFC 4291, written back as RFC 5952 says), and `tools/test_inet.c` holds
both functions to this Mac's, answer by answer - 67 strings in three
families and 788 addresses written - with a control that answers -1
again. The one difference is chosen: Apple's reads an interface's zone
after a `%`, and Kosmos, with no interfaces, reads as glibc does.

And it found that **a process's last words are lost.** `panic` writes
with `kosmos_write`, which the kernel refuses to everything but the
console's owner, so every process that ends in `abort` - every ported
library's failed assertion - ends silent. The message was read with the
check lifted for one run; the cause is on the roadmap.

**A real site's page, 0.11.403.** Diego asked to see the browser render
a real site. Until W7 there is no window and no network loader, so the
nearest true thing is a page saved on the Mac with its files:
Wikipedia's article on BeOS - 344 KB of HTML, two style sheets and 129
pictures, every reference rewritten to a local file - laid out and
painted by `webcoretest.elf` in the guest at 1280 by 1600
(`tools/run_site.py`, not a test: a site's bytes are its authors' and
stay out of the repository). The Vector skin, the contents, the infobox,
its two pictures and the text all came out. One thing it found: a
picture marked `decoding="async"` is decoded by a thread a later frame
picks up, and the harness paints once, so the infobox was empty; a
picture of a page is a snapshot, and WebKit's snapshots paint with
`ForceSynchronousImageDecode`, which the harness now sets.

What is left of W6 is W6d's second half, the recorded sites (Diego's
decisions first: which sites, how they are recorded, where a recording
lives, since a site's bytes are not the public repository's).
