# W6 - WebCore draws a page

JetSki's sixth step (`docs/webkit.md`): WebCore, headless, laying out a
page and painting it with W5e's Skia into a region - the first time a web
page is drawn by WebKit on Kosmos. Written 13 November 2026, the day W5
finished, before any of it is built; both decisions taken by Diego the
same day (*Decided*, at the end).

**What W5 left.** JavaScriptCore runs (W4). Every library WebCore links is
built and held to its own tests: pictures, FreeType and HarfBuzz, SQLite,
libxml2, libpsl, OpenSSL, curl, and Skia drawing every pixel as on this
Mac (`docs/w5.md`).

---

## What W6 is

**A page from a file, laid out and painted, with no window and no
WebKit2.** W7 is where the three processes and the window arrive. Here the
whole of the engine is one program in the guest:

1. **A Kosmos port of WebCore**, `PORT=Kosmos` in WebKit's CMake beside
   `JSCOnly`: WebCore and its platform layer - Skia for graphics, FreeType
   and HarfBuzz for text, the W5a decoders for pictures, curl for the
   network, SQLite for storage, libxml2 for XSLT - with what Kosmos has
   not got turned off (GStreamer, WebGL, WebRTC, accessibility, the
   sandbox, GLib). Kosmos files where WebCore asks the operating system
   something: the clock, threads' run loop on `RunLoopGeneric`, memory
   pressure, the fonts' folder.
2. **A page with empty clients.** WebCore can make a `Page` without
   WebKit2: `SVGImage` does it for every SVG picture, with
   `pageConfigurationWithEmptyClients`. The harness does the same with
   clients of its own where an empty one would not do - a loader strategy
   that reads `/Home` and serves the recorded sites - loads the page, runs
   its scripts and timers to quiescence, lays it out and paints it into a
   Skia surface over a region.
3. **What it says**: the render tree as WebKit's own tests print it
   (`externalRepresentation`, what `DumpRenderTree` prints), a fingerprint
   of the picture, and the load, layout and paint times.

**Size.** Measured at the end of W5: JavaScriptCore's objects for x86-64
are 44 MB and Skia's 20 MB, built without debug information. WebCore has
4,432 source files to JavaScriptCore's 1,329, and generates its DOM
bindings, so its objects should be some hundreds of megabytes, a gigabyte
or two at most. 9.9 GB are free. **It fits**, which `webkit.md` and
`w5.md` had doubted.

## Decisions for Diego

### 1. The source: WebKitGTK's tarball lacks the curl backend

`tools/upstream.py` fetches the WebKitGTK 2.54.2 release, and W4 and W5
were built from it. **It ships only GTK's platform files**: WebCore's
network code is libsoup's (`platform/network/soup`, on GLib), with
PlayStation's two curl files but not `platform/network/curl` itself; no
`NetworkProcess/curl` in WebKit2; no PlayStation, WPE or Windows options in
`Source/cmake`; and no `LayoutTests`. JetSki's design is WebKit on curl,
the PlayStation port's choice, GLib-free.

WebKit's git has a tag for the release, `webkitgtk-2.54.2`, at commit
`b95c91b1c0ee43cc86d25ff7af73038f67a88e04`: the same source the tarball
was cut from, with everything.

- **A. The tarball, and what it lacks from git at the tag's commit**
  (recommended). A sparse, blob-filtered fetch of that one commit, only
  the directories the tarball does not carry - curl's in WebCore and in
  WebKit2, PlayStation's options and platform files where the Kosmos port
  follows them, and the `LayoutTests` W6 is held to - overlaid on the
  tarball's copy, the commit held as libpng's and libwebp's are. Some
  megabytes of source, and some hundreds for the tests chosen. W4 and W5
  are unchanged.
- **B. WebKit's git at the tag, whole**, sparse to `Source/`, `Tools/`
  and the chosen tests, in place of the tarball. One source rather than
  two, at the price of every W4 and W5 build moving onto it and being
  proven again. The full tree with all of `LayoutTests` is several
  gigabytes; sparse, about a gigabyte.
- **C. libsoup, as GTK does.** No new fetch, but GLib and libsoup in the
  process, which the design chose WebKit's PlayStation shape to avoid.

### 2. What a page is held to

`webkit.md` said "compared with one Safari's engine draws on this Mac".
Safari draws with CoreGraphics and CoreText, Kosmos with Skia and
FreeType: every glyph's edge differs, so a picture cannot match exactly,
and a tolerance wide enough for text is wide enough to miss a bug.

- **A. WebKit's own LayoutTests, as text** (recommended). WebKit holds
  itself to tens of thousands of tests whose expected result is text - the
  render tree's boxes and positions, or what the page's script printed -
  much of it the same on every port. A chosen subset, run headless in the
  guest by the harness, each held to its `-expected.txt`, as test262 and
  HarfBuzz's suite are; the count kept as a regression, the failures
  named. **And the pictures** of the recorded sites (`webkit.md`,
  *Testing*) compared with Safari's with a tolerance and looked at by a
  person, as a report rather than a gate.
- **B. The same Kosmos WebCore built for this Mac, under Rosetta**, as
  Skia's reference is, and every pixel held to it. Exact, but it means
  porting WebCore to macOS as a Unix-like system first: the WTF Mac build
  already wanted files the tarball lacks, and it is weeks of work that
  proves the port agrees with itself rather than with WebKit.
- **C. Safari's pictures, with a tolerance**, as the gate. Quick to set
  up, and weak, for the reason above.

## W6a - the source and the port

**The overlay.** `tools/upstream.py`'s `WEBKIT_OVERLAY` names WebKit's git,
the commit `b95c91b1c0ee43cc86d25ff7af73038f67a88e04` and five patterns:
curl's directories anywhere under `Source/`, PlayStation's and WPE's
options, and their platform files. `upstream.webkit_overlay()` checks it out
sparse (`--no-cone`) and blob-filtered, one commit deep, into
`build/upstream/webkit-overlay`, refusing any other commit as every
checkout there does. `webkit_build.py` lays it over its copy of the release
before the patches: **89 files**, 47 of them WebCore's curl backend, and not
one the release has - a file both carry must be the same bytes, or the
build stops, which is what says the two were cut from the same source. The
LayoutTests join the patterns at W6c, when the subset is chosen.

**The port.** `PORT=Kosmos` (`runtime/cxx/jsc.cmake`), in place of JSCOnly:

- `0013-a-port-named-kosmos.patch`: Kosmos in WebKitCommon's list of ports;
  `BUILDING_KOSMOS__` giving `PLATFORM(KOSMOS)` and `BPLATFORM(KOSMOS)`;
  and no Apple SDK looked for on this Mac - WebKit looks before anything
  else whatever it builds for, and JSCOnly's build had found the macOS
  one and never used it.
- `runtime/ports/webkit/Source/cmake/OptionsKosmos.cmake`: the port's
  options. JSCOnly's for now, with WebCore off until W6b.
- `runtime/ports/webkit/Source/WTF/wtf/PlatformKosmos.cmake`: WTF's sources
  for this one system, where JSCOnly's file chose among Windows, Darwin,
  Linux and FreeBSD; it names `SignalsKosmos.cpp` and
  `MemoryFootprintKosmos.cpp`, so 0002 lost its hunk naming one and 0005,
  which only named the other, is gone.

**Held to being the same engine.** JSCOnly configured beside it into a
scratch directory: `cmakeconfig.h` differs in nothing a source reads - three
options only JSCOnly declares, which read as off either way, and the API
tests, which JSCOnly forces on and nothing builds - and a WTF file's flags
differ only in `-DBUILDING_KOSMOS__=1`. A first draft also took
PlayStation's `USE_ISO_MALLOC OFF`, which that comparison caught and which
went: W6a changes the port, not the engine.

**And what uses WebKit's headers says which port it is.** The Makefile
compiles `wtftest.cpp` and `jsc_kosmos.cpp` with WebKit's `cmakeconfig.h`,
and had never given them a port's define - harmless while JSCOnly defined
no `PLATFORM()`, and under Kosmos a library built with `PLATFORM(KOSMOS)`
and callers built without it. `WEBKIT_USER_FLAGS` is now the one place
those flags are, the port's define among them, and `x86-wtf` holds it:
`wtf port=kosmos` leads the line. Control, `make test ONLY=x86-wtf
WEBKIT_PORT_DEFINE=` - `port=none`, and the suite fails.
