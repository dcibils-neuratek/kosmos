S4D3

the keyring keyring.c · keyfile.c · keyproto.hNEW · K2, K4

Doors, not names. smb smbfs alone: get, put, list, forget - kind SMB only. manage Passwords: list without secrets, forget, edit. A request on the wrong door is KEY_ERR_NOT_THIS_DOOR; no operation on manage answers a secret.

Entries in memory, the whole file sealed with AES-256-CCM and written whole at each change. SYS_SENDER asked on each request for the record - "last used by smbfs" - never to decide. A file that does not open is kept aside, never overwritten.

CEL0UEFI

USB driver /Devices/blocksK7

Its read door is every program's and reads any sector of a stick - the boot stick's Kosmos partition too. It refuses that one partition, so /Keyring is no more readable underneath than through diskfs

The loader boot/efi/K8 · DIEGO'S

Reads the UEFI variable KosmosKeyring - boot services only, in the machine's flash - or makes it from the firmware's RNG, and hands the 32 bytes in the boot information. After ExitBootServices nothing on the machine reads it again

System calls
Everything here is a message: one entry a reply, a secret of 16 to 128 bytes once at a sign-in. Nothing recurs on a clock, so nothing needs a region.

Nebula

Threads, address spaces, IPC and capabilities. It does not know what a secret is, and does not learn.

Doors, not names

sender_info's name is what a process said, and from the runner's word in a namespace its parent built. A capability is the one thing a program cannot say it has.

The hash, not the password

smbfs keeps MD4 of the password and nothing else. It opens SMB on that Mac as well as the password would - and the Mac account's password is nowhere here.

No Show

A share's password is not kept to be shown. Other kinds show only behind a lock, which Diego decided against for now.
