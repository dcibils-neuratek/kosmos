What is drawn

  • A share open. Tracker’s sidebar gains a Network group under Drives: the servers seen on the network, and under each one the shares connected from it. Projects on the Mac is open and is listed as any folder is - the same columns, the same sort, the same right click. Three things say it is somewhere else: the globe on the trail, over the network beside it, and the status line, which names the server, the dialect and how fast the files are arriving.
  • Connect to Server. From the Network group’s Connect… or Tracker’s ⋮ menu. An address or a name; the recent ones; then, once the server has answered, a name and a password. The server answers before the password is asked for, so a mistyped address is said at once rather than after a sign-in.
  • Seen, not signed in. nas-salon is on the network and Kosmos has never signed in to it. Its page says what is known without asking it anything more, and offers Sign in.
  • Gone away. The Mac went to sleep with Projects open. The folder stays, greyed, as it was last listed, with a line saying how long ago and when the next try is. Nothing spins and nothing freezes: Tracker draws what it already heard, and the client - which holds the request rather than the window - is what waits (CLAUDE.md, nothing on the desktop waits on a server).
  • Sharing from Kosmos. The Servers window gains File sharing beside Web, Command line and Screen: on or off, the address, which folders of /Home and how, who may sign in, and who is connected now, with a Disconnect. While anybody is connected the strip says so.

Modified is a new column, and only here. Tracker has no Modified column on purpose: a file in /Home is stamped with the counter since boot, which is not a date (tracker.lua’s head). A share’s server stamps real dates, so the column is drawn for a share - and question 5 asks whether that is right.

How servers are seen on the network

The Network group’s servers come from mDNS, which Kosmos does not have. A Mac, a NAS and Windows announce file sharing by multicast DNS - Bonjour - as a service of type _smb._tcp on UDP port 5353, group 224.0.0.251: a pointer to the machine’s name, its port and its address. Every list of servers seen in the drawing - diego-mac, nas-salon, kosmos-t14 - is that answer. Kosmos’s network stack has no multicast and no mDNS, so those rows depend on an mDNS piece that is not built and is not yet on the roadmap.

A typed address works without it. smb://192.168.1.38/Projects is TCP to port 445 and nothing else, and that is all the client needs. A name the router’s DNS knows works through the resolver the network stack already has. A .local name does not: diego-mac.local is answered only by mDNS. So the first client can be built and used with no discovery at all, and the Network group then holds only the servers connected to and the recent ones.

The other direction needs the other half of mDNS. For the M700 to appear in the Mac’s Finder, Kosmos has to announce _smb._tcp itself - a responder, not only a browser. Without it, sharing still works, by address. SMB 1’s NetBIOS browsing, the old way Windows networks listed their machines, is left out with SMB 1.

What is left before any code

This page is the mockup. The roadmap asks for three more things before code, and none of them exists yet:

  • The feature set for the first version: which of the five states, read-only or read-write, which SMB commands, what the client does when a file is open and the server goes.
  • An architecture document, docs/sharing.md or a section of architecture.md: the client’s protocol header, the mount, the regions, how the keyring (if any) is reached, the server’s shape, and what mDNS needs from the network stack.
  • A diagram: Tracker, the namespace, the SMB client, the network stack and the Mac, and the same in the other direction.

Built in the order the roadmap gives: the client first, under QEMU, with the Mac’s own File Sharing as the far end; the server second; discovery when the rest has been lived with.

What is Diego’s to decide

1. Where a share appears in the namespace

/Network/diego-mac/Projects, a tree of its own; or /Drives/Projects on diego-mac, beside the sticks.

/Network, drawn so: a share is not a drive - it goes away for reasons a stick does not, and a program given /Drives is not thereby given the network.

2. Whether passwords are remembered, and where

Asked at every connection; remembered in a file of /Home/Preferences; or remembered by a keyring - a small server holding secrets, which hands the SMB client what it needs to sign in and never hands the password to Tracker. Kosmos has none of these today.

Not decided, and the drawing says so. A keyring is a piece other things will want (the browser’s sign-ins, mail), so it is a kit or a server of its own rather than part of sharing.

3. Read-write in the first version, or read-only first

Opening the Mac’s files here, and Kosmos’s there, read-only to begin with - as FAT32 and exFAT began - or writing from the start.

Read-only first for both, then writing: a bug in reading shows a wrong file, a bug in writing loses one on somebody else’s machine.

4. Guest access

Whether File sharing offers folders to anybody on the network without a password, and whether the client tries a server as a guest before asking.

Off on both sides, drawn so; current Windows refuses guest sign-in by default for the same reason.

5. A Modified column for shares

A share’s dates are real and /Home’s are not, so Tracker would show a column in one place and not in another.

Shown for shares, and in /Home once diskfs stamps the wall clock.

6. Where sharing is set up

In the Servers window, drawn here, or in Preferences, which the roadmap also names.

Servers: it is a server, started, stopped and watched like the other three.
