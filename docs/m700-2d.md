# The desktop on the M700's GPU: 2D first

Diego, 1 October 2026: "lets do gpu 2d acceleration for the m700 so we can
have a faster desktop experience, video decoding and encoding and 3d
acceleration in the future via vulkan driver or opengl". So on the M700 the
desktop comes first, then the video engine (`m700-gpu.md`, the study this
builds on), then 3D (`roadmap.md` 4h, "The M700's order").

**This is the plan to decide from, not a start on the driver.** It leans on
`m700-gpu.md` for the machine, the references and what Kosmos has; what is
new here is what 2D can mean on this GPU, and an order that puts the
cheapest visible win first. Register names are i915's and the PRMs'
(Skylake, Vol 2c *Registers*); every offset is checked against Vol 2c before
it is written into code, as `CLAUDE.md` asks, and none is quoted here from
memory.

---

## The answer, short

- **The M700's blitter copies and fills; it does not blend.** Gen9's blit
  engine (BCS) has colour fills, rectangle copies and raster operations, and
  no per-pixel alpha. The compositor's work is mostly source-over - shadows,
  text, rounded corners, translucent bars - and on this GPU that needs the
  **render engine**: shaders, a pipeline state and a context image, which is
  the Mesa-sized part of a GPU driver and the same work 3D needs.
- **So the first wins are not the blitter.** They are the **display
  engine's**: a **cursor plane**, so the pointer moves without composing -
  what virtio-gpu gave QEMU on 1 October (4h b) - and **page flips** on the
  primary plane, so the compositor draws into a buffer the display then
  shows, and the copy to the screen - 19.8 MB a frame at 3440x1440 -
  disappears. Neither needs command submission, forcewake or a context:
  display registers and entries in the global GTT.
- **Then the blitter**, for the opaque work - a window's interior moved or
  scrolled, a fill - done by the GPU while the processor composes the rest;
  on the foundation the video engine needs too (`m700-gpu.md` 4).
- **Measure first**, as for video: nobody has timed the desktop's frame on
  the M700. The display-engine steps are worth having whatever the number -
  they remove work rather than move it - but the number says how much the
  blitter can buy and where the render engine would.
- **Nothing here runs under QEMU**, which has no Intel GPU: each step is a
  stick and a photograph of what the machine said.

## 1. Where a desktop frame's time goes, today

The compositor (`wm`) composes damaged rectangles of every window into a
frame in memory, a source-over a pixel at a time, four at a time in vector
lanes (`gfx.md` 19.14), and copies the result to the framebuffer the
firmware set up - write-combining since the PC's PAT is programmed
(`hal/pc/fb.c`). Under QEMU `frames` says composing is 84.7% of a busy pass.
On the M700, with real cores and a 3440x1440 screen, nobody knows: how long
composing takes, how long the copy into the framebuffer takes, and what
moving the pointer costs. **Step 1 is to find out**, with the profile the
window manager already keeps, printed on the machine.

## 2. What the GPU offers a desktop, engine by engine

| | What it does | What it needs | For the desktop |
|---|---|---|---|
| **Display engine**: planes | scans a buffer out of the global GTT; a cursor plane over it | its registers; the buffers mapped in the GTT | the pointer for free; flips instead of copies |
| **Blitter** (BCS) | fills, copies, raster ops; tiled or linear | forcewake, a ring or execlists, the GTT | opaque copies and fills off the processor |
| **Render engine** (RCS) | the 3D pipeline: shaders, blending, textures | all of the above, a context image, a shader compiler | windows as textures, blending - the whole compositor |
| Video engines | decode, encode | as the blitter | `m700-gpu.md` |

**The display engine is already running**: the firmware lit the screen and
Kosmos draws into what it set up. The planes are registers on a pipe that is
already on, so reading them changes nothing, and the first step can be a
look before any write.

## 3. The steps, if it goes ahead

Each ends in something the M700 can show, and each is a stick:

1. **Measure the desktop** on the M700: the window manager's profile of a
   busy minute - composing, the copy to the screen, the pointer - printed by
   a program and read off a photograph. No new code beyond what prints it.
2. **Find it and look**: the GPU's device ID, BAR0 mapped (`SYS_DEV_MAP`'s
   bound raised for it - `m700-gpu.md` 6), and the display's state read
   back without writing: which pipe drives the screen, its plane's surface
   address, stride and format, where in the GTT the firmware put the
   framebuffer. `diagnose` says what it found.
3. **The cursor plane**: a 64 by 64 picture in a page the driver owns,
   entered in the global GTT, and the cursor's control, base and position
   registers. **The pointer moves composing nothing.** *Built, 17 October,
   and not through the HAL as this first said*: the driver is a process,
   `intelgpu` at `/Devices/gpu`, and the window manager asks it through
   `gpu.lua` - the cursor's set, move and hide - when `gfx.cursor`, the
   kernel's virtio-gpu entries, says no. A display engine's driver belongs
   at EL0 like every other driver here; the HAL's three entries stay for
   the display the kernel drives itself. 3a was the driver's own test
   picture (`testing.md` 18.659), 3b the window manager's arrow (18.660).
4. **Page flips, shaped for the 3D compositor** (below, *Step 4, planned
   for 3D*): buffers the driver owns and maps in the GTT, shown by a flip
   the display latches at vertical blank, and the window server told when
   it has - no tearing, and the shape a GPU compositor and a full-screen
   game both present through.
5. **The blitter's foundation**: forcewake, the global GTT, a ring on the
   blit engine, a batch that stores a value to memory - `m700-gpu.md` steps
   2 to 4, on BCS rather than the video engine. Ring buffer first, execlists
   if it will not run.
6. **Fills and copies on the blitter**: the compositor's opaque rectangles
   handed to it, compared pixel for pixel with what the processor draws.
7. **Later, the render engine**: blending on the GPU, windows as textures -
   the step that makes the compositor the GPU's, and the same machinery 3D
   through Vulkan or OpenGL stands on.

**What can be checked without the machine** is what is pure C: a blitter
command built into its words, a GTT entry, a cursor picture's format - held
to Vol 2a/2c and to Mesa's `genxml/gen90.xml` on the Mac, as `fat_decode.c`
is held to a disk.

**Effort.** Steps 2 to 4 touch only the display engine, which is running and
documented, and give the pointer and the copy back; a few sticks. Step 5 is
the risky one, for the reasons `m700-gpu.md` 7 gives - a GPU that ignores a
command says nothing - and it is shared with video. Step 7 is a project of
its own.

## 4. What is Diego's to decide

1. **The order**: the display engine first (cursor, then flips), then the

## Step 4, planned for 3D

Diego, 17 October 2026, as step 4 started: "Remember we want to do 3d
composition in the future as welll as 3d acceleration", "For games and
apps", "So plan for it". Before that, the same day: "Is not only 2d is also
3d to be able to play 3d games in the future and have a 3d compositor for
the desktop for effects like translucent and glass and animations".

So a flip is not built as "a second framebuffer for the processor's
compositor". It is built as the first piece of what every GPU desktop
presents through - Linux's KMS, Wayland's compositors, a game's swap chain
- and the processor's compositor is only its first user.

### The pieces, and who uses them later

| Piece | Step 4, with the processor composing | Later, with the render engine (step 7) |
|---|---|---|
| **A GPU buffer**: pages the driver owns, mapped in the global GTT, handed out as a region | the window server's two screen buffers | render targets and textures: every window's buffer, the compositor's output, a game's swap chain |
| **A flip**: a buffer's GTT address written to `PLANE_SURF`, latched by the display at vertical blank | the window server shows the buffer it finished | the same: what the GPU compositor rendered, or a full-screen game's own buffer, shown with no copy at all |
| **Flip done**: the driver says when the display took it (`PLANE_SURFLIVE`, `PIPE_FLIPCOUNT`) | the window server knows which buffer is free to compose into | a game's frame pacing; the compositor's 60 frames a second |
| **Buffer age**: each buffer knows which frame it last held | damage composed into the hidden buffer is this frame's and the last's | the same rule; GPU compositors use it (EGL's buffer age) |

The buffer is the load-bearing decision. **A window's pixels, a game's
frame and the screen will all be GPU buffers**, so that the render engine
can sample one and write another, and the display can scan any of them
out. Step 4 makes the screen's two of them; when windows' buffers move
into GPU memory (step 7) they are the same object, made by the same verb.

### The protocol (`gpuproto.h`)

- `GPU_OP_BUFFER_NEW` (pages, flags) -> a region with the message, and its
  GTT address. The driver allocates, enters the pages in GTT slots of its
  own past the firmware's framebuffer and the cursor's, and keeps the
  buffer; the caller holds the region. Its flags say *scanout* (the display
  may show it: aligned as the plane needs, linear, the stride a multiple of
  64 bytes) - later *render target*, *texture*, tiled.
- `GPU_OP_FLIP` (buffer, the plane) -> answered at once, never at the vertical
  blank: *nothing waits on hardware* (`design.md` §2). The driver writes
  `PLANE_SURF`, which the display holds until the next blank.
- `GPU_OP_FLIPPED` -> the flip count and which buffer the display is
  scanning, read from `PIPE_FLIPCOUNT` and `PLANE_SURFLIVE`. The window
  server asks before composing into the buffer it last showed, and composes
  into it only once the display has left it. Polling first; the display's
  vblank interrupt, claimed by the driver, when a pulse (`pulses.md`) can
  carry it without a reply.
- A buffer is held by whoever holds its region, and the driver gives its GTT
  slots back when nobody does - the same "an endpoint ends with its
  process" rule as the rest.

Who may flip: only the holder of the screen, as `kosmos_screen_take` says
now - the window server, or a full-screen game it lends the plane to.

### Where the time goes, and what is measured first (4a)

Composing into a GPU buffer with the processor has a cost the plan has to
name: the display does not snoop the processor's caches. So either the
buffer is write-combining for the processor - writes fine, reads very slow,
and source-over *reads* the destination - or it is cached and every line
composed is flushed (`clflush`) before the flip. Or the window server keeps
composing into its cached back buffer and copies the damage into the hidden
screen buffer, which is today's copy, tear free.

**Which one is a measurement, not an opinion**, so 4a comes first: the
window server times its copy to the screen apart from its composing, on the
M700, under the drag of 18.657. Then:

- if the copy is a small part of a pass, 4b keeps it, and flips buy no
  tearing and the GPU-buffer foundation - which is the point of step 4 for
  3D anyway;
- if it is a large part, 4b composes into the cached screen buffer and
  flushes, and the copy goes.

Either way, **the copy disappears for good in step 7**, when the render
engine composes into the buffer the display shows.

**Measured, 17 October** (`testing.md` 18.661): Diego dragging a window,
the copy is 0.45 ms of 1.82 a frame - **25%** - so 4b keeps it. And the
desktop composed **514 frames a second** for a 60 Hz screen, one for each
of the mouse's reports. So 4b also gives the window server a beat: compose
at most once a refresh, the frame shown by a flip at vertical blank, and
the pointer's reports between frames moving only the cursor plane.

### Vulkan and OpenGL ES, on the same buffers

Diego, 17 October: "We might want to do a vulkan or OpenGL ES Driver".
That is the applications' half of step 7: Mesa's Intel drivers - `anv`
for Vulkan, `iris` for OpenGL and OpenGL ES - built into a program's own
process, as a kit, over a Kosmos GPU server that hands out buffers,
contexts and submission with a declared protocol. What they render into
and present from is the GPU buffer of step 4: a window's swap chain is a
few of them, handed to the window server - or, full screen, flipped by the
program itself (4c). Nothing in step 4 is built for the processor's
compositor alone.

### The steps

- **4a** the copy timed apart in the window server (`frames` says it).
- **4b** `GPU_OP_BUFFER_NEW`, `GPU_OP_FLIP` and `GPU_OP_FLIPPED` in the
  driver; the window server given two scanout buffers on the M700, composing
  by buffer age and flipping; the firmware's framebuffer shown again when
  the window server lets go, as the console's screen is now. Diego looks for
  tearing with a window dragged fast.
- **4c** a full-screen program flips its own buffers - the shape a game
  takes - with the window server out of the path while it does.

Under QEMU there is no Intel GPU: the window server copies as it does
today, and the gate keeps holding that path.
