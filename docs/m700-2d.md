# The desktop on the M700's GPU: 2D first

Diego, 1 October 2026: "lets do gpu 2d acceleration for the m700 so we can
have a faster desktop experience, video decoding and encoding and 3d
acceleration in the future via vulkan driver or opengl". So on the M700 the
desktop comes first, then the video engine (`m700-gpu.md`, the study this
builds on), then 3D (`roadmap.md` 4h, "The M700's order").

**This is the plan to decide from, not a start on the driver.** It leans on
`m700-gpu.md` for the machine, the references and what Kosmos has; what is
new here is what 2D can mean on this GPU, and an order that puts the
cheapest visible win first. Register names are i915's and the PRMs'
(Skylake, Vol 2c *Registers*); every offset is checked against Vol 2c before
it is written into code, as `CLAUDE.md` asks, and none is quoted here from
memory.

---

## The answer, short

- **The M700's blitter copies and fills; it does not blend.** Gen9's blit
  engine (BCS) has colour fills, rectangle copies and raster operations, and
  no per-pixel alpha. The compositor's work is mostly source-over - shadows,
  text, rounded corners, translucent bars - and on this GPU that needs the
  **render engine**: shaders, a pipeline state and a context image, which is
  the Mesa-sized part of a GPU driver and the same work 3D needs.
- **So the first wins are not the blitter.** They are the **display
  engine's**: a **cursor plane**, so the pointer moves without composing -
  what virtio-gpu gave QEMU on 1 October (4h b) - and **page flips** on the
  primary plane, so the compositor draws into a buffer the display then
  shows, and the copy to the screen - 19.8 MB a frame at 3440x1440 -
  disappears. Neither needs command submission, forcewake or a context:
  display registers and entries in the global GTT.
- **Then the blitter**, for the opaque work - a window's interior moved or
  scrolled, a fill - done by the GPU while the processor composes the rest;
  on the foundation the video engine needs too (`m700-gpu.md` 4).
- **Measure first**, as for video: nobody has timed the desktop's frame on
  the M700. The display-engine steps are worth having whatever the number -
  they remove work rather than move it - but the number says how much the
  blitter can buy and where the render engine would.
- **Nothing here runs under QEMU**, which has no Intel GPU: each step is a
  stick and a photograph of what the machine said.

## 1. Where a desktop frame's time goes, today

The compositor (`wm`) composes damaged rectangles of every window into a
frame in memory, a source-over a pixel at a time, four at a time in vector
lanes (`gfx.md` 19.14), and copies the result to the framebuffer the
firmware set up - write-combining since the PC's PAT is programmed
(`hal/pc/fb.c`). Under QEMU `frames` says composing is 84.7% of a busy pass.
On the M700, with real cores and a 3440x1440 screen, nobody knows: how long
composing takes, how long the copy into the framebuffer takes, and what
moving the pointer costs. **Step 1 is to find out**, with the profile the
window manager already keeps, printed on the machine.

## 2. What the GPU offers a desktop, engine by engine

| | What it does | What it needs | For the desktop |
|---|---|---|---|
| **Display engine**: planes | scans a buffer out of the global GTT; a cursor plane over it | its registers; the buffers mapped in the GTT | the pointer for free; flips instead of copies |
| **Blitter** (BCS) | fills, copies, raster ops; tiled or linear | forcewake, a ring or execlists, the GTT | opaque copies and fills off the processor |
| **Render engine** (RCS) | the 3D pipeline: shaders, blending, textures | all of the above, a context image, a shader compiler | windows as textures, blending - the whole compositor |
| Video engines | decode, encode | as the blitter | `m700-gpu.md` |

**The display engine is already running**: the firmware lit the screen and
Kosmos draws into what it set up. The planes are registers on a pipe that is
already on, so reading them changes nothing, and the first step can be a
look before any write.

## 3. The steps, if it goes ahead

Each ends in something the M700 can show, and each is a stick:

1. **Measure the desktop** on the M700: the window manager's profile of a
   busy minute - composing, the copy to the screen, the pointer - printed by
   a program and read off a photograph. No new code beyond what prints it.
2. **Find it and look**: the GPU's device ID, BAR0 mapped (`SYS_DEV_MAP`'s
   bound raised for it - `m700-gpu.md` 6), and the display's state read
   back without writing: which pipe drives the screen, its plane's surface
   address, stride and format, where in the GTT the firmware put the
   framebuffer. `diagnose` says what it found.
3. **The cursor plane**: a 64 by 64 picture in a page the driver owns,
   entered in the global GTT, and the cursor's control, base and position
   registers - `hal_cursor_set`, `_move` and `_hide` on the PC board, the
   entries virtio-gpu earned, so the window manager hands its arrow over
   exactly as it does under QEMU. **The pointer moves composing nothing.**
4. **Page flips**: a second framebuffer in the GTT, the compositor drawing
   into whichever is not shown, and the plane's surface register written at
   vertical blank - the copy to the screen gone, and no tearing.
5. **The blitter's foundation**: forcewake, the global GTT, a ring on the
   blit engine, a batch that stores a value to memory - `m700-gpu.md` steps
   2 to 4, on BCS rather than the video engine. Ring buffer first, execlists
   if it will not run.
6. **Fills and copies on the blitter**: the compositor's opaque rectangles
   handed to it, compared pixel for pixel with what the processor draws.
7. **Later, the render engine**: blending on the GPU, windows as textures -
   the step that makes the compositor the GPU's, and the same machinery 3D
   through Vulkan or OpenGL stands on.

**What can be checked without the machine** is what is pure C: a blitter
command built into its words, a GTT entry, a cursor picture's format - held
to Vol 2a/2c and to Mesa's `genxml/gen90.xml` on the Mac, as `fat_decode.c`
is held to a disk.

**Effort.** Steps 2 to 4 touch only the display engine, which is running and
documented, and give the pointer and the copy back; a few sticks. Step 5 is
the risky one, for the reasons `m700-gpu.md` 7 gives - a GPU that ignores a
command says nothing - and it is shared with video. Step 7 is a project of
its own.

## 4. What is Diego's to decide

1. **The order**: the display engine first (cursor, then flips), then the
   blitter - rather than the blitter first.
2. **Measuring first** (step 1), with a stick, before any driver code.
3. **`SYS_DEV_MAP`'s bound raised** for this device and **no IOMMU** for
   now, as `m700-gpu.md` 8 asks for video.
4. **A stick for each step**, since none of it runs under QEMU.
