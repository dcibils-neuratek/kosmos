Kosmos IDE

Where Lua for Kosmos is written and run: a tree of the project, an editor that knows the system it is on - what ui, fs and gfx offer, read from the libraries themselves - a button bar with Run and Stop at its middle, and every line checked as it is written. The editor is Cafesa3D's Script panel's, grown into a window of its own. Drawn before it is written, and agreed as drawn.

What each part is for

The tree is a folder and everything under it - /home/development as drawn, the tutorial's ten lessons - and under it, read only, Kosmos itself: /bin, /lib and the kits, so the way to learn what ui.slider does is to open ui.lua and read it. A Lua file runs from its row as well as from the button. Outline is the file's functions, in order.

The editor colours Lua as it is typed - keywords, strings, numbers, comments, calls, and the names a library gave you in a colour of their own - numbers its lines, marks the line the cursor is on and every line with something wrong. It is the one Cafesa3D's Script panel uses: text, the cursor, selection, undo and colouring are one component, grown out of the kit's ui.editor, which says of itself "no undo, no selection, no syntax colouring".

Suggestions come from the system the IDE is running on, not from a list someone keeps: after ui. they are the names ui.lua actually returns, after win: a window's methods, after gfx. the graphics kit's, and the file's own locals throughout. What each one is comes from the comment above it in its source - the libraries here are written to be read, so their comments are the documentation. Tab or Enter takes one; typing on narrows them.

Run starts the file as its own process, the way the prompt runs ./converter.lua: a program's print goes to Output, an application's window opens on the desktop, and the IDE stays answering whatever the program does. Stop ends it. Output says how it ended - its exit code, or the error and the line, which is a click away. A file that is not saved is run as it is on the screen.

How it checks

What would stop it running is Lua's own parser, run as you type: the same parser that will run it, so a line it refuses is exactly the line Lua would - "'end' expected (to close 'function' at line 19) near <eof>" - marked in red, with nothing guessed.

What would go wrong once it runs is a linter: a name used and never set, a local set and never used, one that hides another, a global where a local was meant. luacheck is proposed - MIT, written in Lua, and it reads Lua 5.4 - taught what a Kosmos program is given, which is the list tools/luaglobals.py already holds the tree to, so use and fs are known and io is "a Kosmos program has no io; files are fs".

And what only Kosmos knows: a name the library does not have - ui.slidr - is found by asking the library, the same way suggestions are made, with the nearest name it does have. Problems lists them all; a click goes to the line. Nothing is fixed without asking.

Decided

Diego, 26 September: "the mockup is perfect!!!" - and the six questions this page asked, answered:

  • The checker is luacheck, vendored and taught Kosmos's names, with Lua's own parser before it.
  • A run's output goes to the Output panel.
  • An ordinary window - resized, minimised and maximised as needed, not opened maximised. Which settles how it is built: from the kit's widgets, because the window manager resizes a window that sends it drawing and never one with a surface of its own.
  • It follows the look chosen in Preferences, light or dark; the toggle above only shows both.
  • It opens on the last project opened - the tutorial's lessons the first time.
  • Debugging is a later step of its own.

And the lessons in its tree are wanted as drawn, one to ten, from a window with a button to a 3D app (roadmap.md 7) - the IDE's first project.

Asked for after using it - 27 September

Diego, on the 0.10.172 stick: "the ide looks great!" - and three things it is missing. Two follow what the system already has and are built as it has them; the third is new, so it is drawn here first.

A scrollbar on the editor - "to see where we are on the file": the kit's own, the one every list has, so it looks like the rest of the look chosen, and dragged it goes there.

Text larger and smaller - "like we have in the terminal app": Larger text, Smaller text and Actual size in the ⋮ menu, as Terminal and Log View have them, and Ctrl = and Ctrl -. The editor and Output both; kept for tomorrow.

Find a file - "an ide wide search field to find files easily by name or part of name": a field at the header's right, where Tracker keeps its Search, and Ctrl P to it. Every file the tree reaches - the project, /bin, /lib - whose name has what is typed in it, the files whose names begin with it first; where each lives beside it, and whether it is an application, a program or a library, because two files can share a name and be unrelated (/lib/clock.lua is the local time, not the Clock).
