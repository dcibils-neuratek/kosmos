# W4 - JavaScriptCore on Kosmos

*Planned 11 November 2026, the day W3 was finished. Its source fetched,
not committed - Diego's choice the same day.*

JetSki's step W4 (`docs/webkit.md`): `jsc`, JavaScriptCore's shell, built
for Kosmos with the LLInt - its interpreter - and no JIT, running a
script; then test262's language tests counted, and the count kept as a
regression. The first time anything of WebKit runs here.

**In short.** Five parts, each leaving a test. The C++ runtimes again,
with threads, on the POSIX layer; ICU, which WTF and JavaScriptCore
include from their first file; WTF and bmalloc; JavaScriptCore and `jsc`
in an image of their own; and test262.

---

## Where the source comes from

**Fetched, not committed** (README's decision log, 11 November). Each
release tarball goes into `build/downloads/`, is held to its published
SHA-256 before anything reads it, and is unpacked under `build/`. What
the tree carries is Kosmos's: the toolchain file, the CMake cache of
options, the port's few source files, and patches as files the build
applies - a patch is a build step somebody can read, as `lua/patches/`
is for Lua.

- **WebKitGTK 2.54.2** (23 October 2026), 47.7 MB, SHA-256
  `a76345b391bef6211fb5ab6cfab2e86b285d18cda17cbb9ade595f1252b86065`, from
  `webkitgtk.org/releases/`, its sum from the `.sums` file beside it. The
  GTK release tarball rather than WebKit's repository: it is WebKit's code
  at a release, it carries `OptionsJSCOnly.cmake` - the JSC-only port,

- **ICU 79.1** (22 October 2026), `icu4c-79.1-sources.tgz`, 28.2 MB,
  SHA-256 `06fa63ecb521048f8082f12ad988f6b678d90cbd88aafce24cbc94902b191d99`,
  GitHub's digest for the release asset; and `icu4c-79.1-data-bin-l.zip`,
  the little-endian data already built, 12.9 MB, SHA-256
  `72489fb316a60ae1c1da205866edd01b17e8fbf8354ad0615e6cc60f74e08811`.

## The port, in one paragraph

**JSCOnly, the Generic event loop, static.** WebKit has a port that
builds JavaScriptCore and nothing else (`OptionsJSCOnly.cmake`), and its
event loop needs no GLib - a `RunLoop` on WTF's own threads and timers.
Built static (`ENABLE_STATIC_JSC`), so it links into an image as every
kit here does, and with the JIT off (`ENABLE_JIT=OFF`, the LLInt and the
C loop's fallback where the offline assembler has no backend), so nothing
the process writes is ever run: the JIT's two mappings of one region,
which W2 built, wait for the JIT's own step (below). A Kosmos `OptionsKosmos.cmake` is not needed at
first: JSCOnly with the Kosmos toolchain file and a cache of options, as
the runtimes are built (`runtime/cxx/`).

## W4a - the C++ runtimes, with threads

libc++ was built with threads, the monotonic clock and the random device
off (`runtime/cxx/runtimes.cmake`), because there was nothing to build
them on. W3 built it: pthreads, `clock_gettime`, `getentropy`. ICU and
WTF use `std::mutex`, `std::condition_variable` and `std::atomic`, and
libc++abi's guard for a function's statics wants a lock. So the runtimes
are configured again with threads on, against the POSIX layer's headers,
and the images that link them link the layer too. *Test*: `cxxtest.elf`
gains `std::thread`, a `std::mutex` held by two, and a static initialised
once by two threads racing for it.

*Built, 0.11.381* (`testing.md` 18.776). Threads, the pthread API and the
monotonic clock on in all three runtimes; the layer's headers first on
the include path, before even the compiler's, because each of them
reaches the next with `include_next` and that finds only what comes
after. libc++ asked one thing the layer lacked, `strerror_r`, and has it.
And the build now configures the runtimes again when their options or
toolchain change: CMake reads an initial cache only when it configures,
so a build made before this one kept threads off however the file read -
a fresh configure writes `.configured`, and a newer options file than
that starts again.

## W4b - ICU

ICU 4C's `common` and `i18n`, compiled by clang with the toolchain file
into `libicuuc.a` and `libicui18n.a` - by a list the build keeps rather
than ICU's `configure`, which cannot run a Kosmos program to learn about
one, as FFmpeg's could not (`tools/ffmpeg_vendor.py`). The data is the
prebuilt little-endian `icudt79l.dat`, linked into the image that needs it
under the name ICU looks for its common data by, so no file is opened for
it; trimmed later with ICU's data filter when its size
is worth the work. *Test*: an image that normalises, collates, breaks a
sentence into words and formats a number in two locales, each against
the answer ICU gives on this Mac.

*Built, 0.11.382* (`testing.md` 18.777). All 456 files of `common` and
`i18n`, unedited, by `tools/icu_build.py`, which says as defines what
`configure` would have found: no time zones (UTC, offset 0), no
`nl_langinfo`, a `wchar_t` of UTF-32, no wide-character functions. The
data needs no `udata_setCommonData`: an object built by the script defines
`icudt79_dat`, the symbol ICU's `udata.cpp` already looks for, and the
33.5 MB are in the image. What ICU asked of the rest of the system: `atol`
and `atoll`; `LC_CTYPE` and `LC_MESSAGES` (both answered "C", which ICU
reads as `en_US_POSIX`); `expf`, `tanhf` and `modf` from musl's tarball,
as its other maths came; `atan2f` and `atan2l` declared for libc++'s
`<complex>`; and a `wcslen`, because clang turns a loop counting
`wchar_t`s into a call to it. decNumber includes `<signal.h>` for a trap
ICU has switched off, so ICU alone has an empty one, in
`runtime/ports/icu/include/` - the POSIX layer has no signals and does not
pretend to. The image, `icutest.elf`, is 64.5 MB stripped.

## W4c - WTF and bmalloc

The first of WebKit: WTF and bmalloc (and libpas inside it) through
CMake, JSCOnly, static. Where WTF asks for something the POSIX layer
does not have, the layer grows it, or WTF's Kosmos file says what to do
instead - `fork` and signals never. *Test*: WTF's own `RunLoop` and a
`WTF::Thread` started, a `HashMap` and a `String` doing their work.

*Built, 0.11.383* (`testing.md` 18.778). WebKitGTK 2.54.2's WTF and
bmalloc, for both architectures, by `tools/webkit_build.py`. It cuts a copy of the
release into `build/webkit/src` and applies `runtime/patches/webkit/`,
then lays Kosmos's own files in from `runtime/ports/webkit/`. CMake
configures it with `runtime/cxx/jsc.cmake` and the toolchain, and ninja
builds it. The release itself is never edited. CMake configures again when
the patches, the options, the runtimes or a libc or POSIX header change:
a header that arrived after a configure was otherwise remembered as
missing. That is how `HAVE_LOCALTIME_R` stayed 0 after `localtime_r`
came.

Five patches, each with its reason at the top:

- **0001, Kosmos is an OS:** `__kosmos__` is `OS(KOSMOS)` and `OS(UNIX)`.
- **0002, a thread stopped by Nebula:** WTF's suspend, resume and
  registers on `pthread_suspend_np`, `pthread_resume_np` and
  `pthread_getregs_np`, which are `SYS_THREAD_SUSPEND`, `SYS_THREAD_RESUME`
  and `SYS_THREAD_REGS`, with WTF's signal handlers kept and never
  delivered (`SignalsKosmos.cpp`). This is how JavaScriptCore's collector
  will stop a thread to scan it, and it needs no signal to do so.
- **0003, Int128 without iostreams:** a libc++ without localisation has
  no `std::ostream`, so the two operators that print to one are left out
  there. libc++'s locales have been on since 19 November 2026 (`gpu3d.md`
  G2), and the patch is kept until it is taken out on its own
  (`roadmap.md`).
- **0004, paths and temporary files:** a path is UTF-8 bytes and is made
  from them, since libc++ has no `char8_t` conversion without
  localisation. Temporary files go in `/Temporary`, because a process has
  no environment to say TMPDIR.
- **0005, the memory footprint:** WTF's footprint comes from Nebula's
  process table (`MemoryFootprintKosmos.cpp`). The patch only named that
  file in `PlatformJSCOnly.cmake`, and went with W6a (`docs/w6.md`), when
  Kosmos became a port of its own and WTF's sources were listed in
  `PlatformKosmos.cmake`; 0002's line naming `SignalsKosmos.cpp` went the
  same way.

bmalloc runs on the system's malloc for now; libpas on W2's reservations is
its own step.

**What it asked of the rest**, and each part has its own rule:

- **libc++ now has `std::filesystem`** (`runtimes.cmake`), because WTF's
  FileSystem is written on it.
- **The POSIX layer grew what that library and WTF call:**
  - `openat`, `unlinkat`, `fdopendir` and `fchmodat`. A descriptor
    remembers the path it opened, so a name relative to one is that path
    plus the name.
  - `sendfile`, which is how libc++ copies a file - with its streams only
    where `sendfile` cannot, since its locales were turned on.
  - `mkstemp`, `mkostemp`, `mkdtemp`, `msync` and `_exit`.
  - `pthread_attr_setstack`, `sched_param` and the scheduling calls.
  - `posix_footprint_np`.
  - Calls that are named and refused, each with its reason:
    `utimensat`, `futimens` and `utimes` (a file's times are its server's);
    `readlink`, `link` and `symlink` (there are no links); `statvfs`
    (nothing asks a server how much room it has yet); `flock` (the servers
    keep no locks); `chdir` anywhere but where the process is; and a
    thread stack the caller placed (a thread's stack is its slot).
- **The libc grew** `strnlen`, plus `fegetround` and `fesetround`, which
  WebKit's SIMD library calls on ARM. `fenv.h` had said those would never
  be declared. Nebula saves each thread's FPCR and MXCSR, so a mode set in
  one thread stays that thread's, and the header now says so.
- **ICU's installed `uconfig.h` begins with the defines it was built
  with**, as ICU's own install writes them. Without those, WTF called
  `u_strToUpper_79` into a library that has `u_strToUpper`.

*The test*, `wtftest.elf`, says one sentence, piece by piece:

- WTF's strings;
- a hash map of a thousand keys;
- four threads counting into one atomic;
- a spinning thread suspended (its counter stands still between two
  windows in which it is seen moving), its stack pointer read inside its
  own stack, and then let go;
- the run loop, with three functions queued, a fourth sent from another
  thread, and a timer that waits;
- a thread rounding down while the main thread still rounds to nearest;
- files through std::filesystem, made, copied, listed and removed as a
  tree.

It passes on x86-64 and AArch64. Each control was a separate build:

| Control | Piece of the sentence | Result |
|---|---|---|
| Suspension and register read as no-ops | suspend | `ran/sp-elsewhere` |
| `fesetround` that changes nothing | rounding | `same` |
| `unlinkat` that refuses | files | `left` |

## W4d - JavaScriptCore and `jsc`

JavaScriptCore with the LLInt, and `jsc` linked into `jsc.elf` - an
application installed in `/Home/Apps/JSC` as Doom is, its image with the
engine, ICU and its data - and `LICENSE` then lists ICU's terms (the
Unicode Licence v3) and WebKit's, as it lists Doom's for `doom.elf`, since
that image is installed where `icutest.elf` never is. The offline
assembler is Ruby, run on the host during the build (`/usr/bin/ruby`). *Test*: `jsc` running a script that
exercises the language - closures, classes, generators, `async`, a
`Proxy`, a regular expression, `Intl` - and printing what it computed.

*Built, 0.11.384* (`testing.md` 18.779). JavaScriptCore with the LLInt,
for both architectures, by `tools/webkit_build.py`. `jsc.elf` holds the
engine, WTF, bmalloc, ICU and its data, the POSIX layer and the C++
runtimes, and it is installed in `/Home/Apps/JSC` beside `jsc.lua`:

    jsc script.js
    jsc -e "print(6 * 7)"

**Not `jsc.cpp`.** WebKit's own shell is 4,700 lines of WebKit's test
harness: command-line flags, `$vm`, signal handlers, and environment
variables a test runner sets. Almost none of it is about running a script.
So `user/installed/JSC/jsc_kosmos.cpp` drives the engine through its
public C API, the one an embedder uses, and gives the script one function,
`print`. A file's bytes go from the disk to the engine without passing
through Lua. test262 (W4e) needs `$262` from the shell it runs in, which
is a few functions more there.

Six more patches, each with its reason at the top:

- **0006, Kosmos is ELF:** the interpreter is one large `asm` statement,
  and its labels are spelled as ELF's.
- **0007, the collector on Nebula:** a stopped thread's stack pointer is
  read under the name `pthread_regs_np` gives it. There is no `mincore`,
  because nothing on Kosmos is paged out, as WebKit's comment already says
  of QNX.
- **0008, no dynamic loader:** the bytecode cache is versioned by the
  build's timestamp, as on Haiku and QNX, since there is no `dladdr` to
  find the library's build ID with.
- **0009, randomness from Nebula:** WTF's random device fills each request
  with `arc4random_buf`, which is `SYS_ENTROPY`, in Fuchsia's shape,
  rather than opening `/dev/urandom`.
- **0010, code written then run, on ARM:** the ARM64 assembler's cache
  flush is the compiler's `__builtin___clear_cache`. EL0 may do that
  because Nebula sets `SCTLR_EL1.UCT` and `.UCI`. Nothing calls it while
  the JIT is off, but the header is compiled either way.
- **0011, a global on ARM:** the interpreter reaches a global such as
  `g_config` with `adrp` and `add`, as on Windows. A Kosmos image is
  static and never relocated, so there is nothing for a GOT to do.

What it asked of the rest:

- **Twenty-five more of musl's maths functions** (`exp2`, `fma`, the
  inverse hyperbolics, `lrint`, `nextafter` and the `float` halves of the
  trigonometry), by the closure over undefined symbols that chose the
  others. musl's `atomic.h` came with them, for `fma`'s count of leading
  zeros. FFmpeg's `config.h` is held to `math.h` (`tools/ffmpeg_vendor.py`),
  so twelve of its `HAVE_` maths switches turned on. That brought
  `atan2f`, which `math.h` had declared since W4b and nothing defined.
- **`__cxa_atexit` and `__dso_handle`**, in the POSIX layer. C++ registers
  every static's destructor, but a process that ends gives everything back
  to Nebula at once, so the destructors are accepted and never run.
- **`libJavaScriptCoreJIT.a`:** the bytecode, its compiler and the
  interpreter's glue are a CMake object library of that name even with the
  JIT off. The script packs it into an archive, so the Makefile links one
  more library rather than fifty objects.

`LICENSE` lists ICU's terms (the Unicode License v3) and WebKit's (the
LGPL 2 and BSD), since `jsc.elf` is installed where `icutest.elf` never
is.

## W4e - test262

**Built, 0.11.385.** test262's language tests, run by JavaScriptCore in
the guest and counted: **22,408 of 23,015 pass, 97.4%**, with 817 module
tests not run. A full run takes two minutes in eight x86-64 guests side by
side.

**Outside the gate** (Diego, 12 November 2026, the recommendation over a
sampled slice in the gate or all of it there). `make test262` runs it, and
`bench/test262.json` keeps the commit it was counted against and every
test that failed. A run fails when a test that passed there fails now, and
names the tests that newly pass; `make test262 UPDATE=1` keeps a run as the
new baseline. `ONLY=` a pattern of the tests' paths holds one directory to
the baseline for just the tests it ran, in under a minute.

**Fetched by git, at a commit.** test262 publishes no releases and no sums,
so `tools/upstream.py` fetches it at 2e58f87 (11 November) only as deep as
that one commit, and refuses it unless git says that is what it holds and
nothing in the checkout changed. A commit's name is the hash of what is in
it, which is the sum its publisher gives.

**How a test runs.** The host reads each test's front matter and writes a
bundle per guest: the harness's files once, then each test with its flags,
its includes and what it is expected to throw. `jsc_kosmos.cpp` composes
each case as test262's own runners do: `assert.js`, `sta.js`,
`doneprintHandle.js` for an `async` test, its includes, then the test,
with `"use strict";` first in strict mode. It then runs it in a global
object of its own, in a VM all of them share. A test with neither
`onlyStrict` nor `noStrict` runs twice. A negative test at the parse phase
is held to `JSCheckScriptSyntax`'s error, which never runs it; at runtime,
to what it threw. An `async` test passes when it prints that it completed.
A case that brings the program down is counted as failed and the guest
carries on from the next; one that says nothing for 150 seconds gets its
guest booted again.

**`$262`**, in every global: `createRealm` (a new global in the same VM),
`evalScript`, `detachArrayBuffer` (by `ArrayBuffer.prototype.transfer`,
which detaches its source; the C API has no other way), `gc` (a collection
that has finished when it returns) and `global`. `agent`, which is threads
with VMs of their own, is not there; the one language test that asks for it
fails, counted.

What failed, all 607:

| | tests | why |
|---|---|---|
| a module loader | 287 | `import()` from a script: the C API evaluates scripts, and the driver gives the engine no loader. The 817 module tests wait on the same thing. |
| `import defer`, `import source` | 148 | proposals JavaScriptCore 2.54 does not have |
| `using`, `await using` | 108 | explicit resource management, which 2.54 does not have either |
| the rest | 64 | classes' edge cases, direct `eval`, `with` and a few more: where JavaScriptCore 2.54 and the specification disagree, which nothing on Kosmos changes |

What it found on Kosmos, which was the point of running it here:

- **`mprotect` of no bytes was refused.** JavaScriptCore reserves what a
  resizable buffer may grow into, protects the part past what it holds,
  and ends the program if the protection fails. When the most it may hold
  rounds to the 64 KB it has, the part is no bytes. Linux returns success
  for that and Kosmos returned EINVAL, so seven tests ended the program.
  `mprotect` and `madvise` of no bytes succeed now, and `posixtest.elf`
  holds them to it.
- **Each case's garbage was left to the heap.** A global object per case,
  and the heap, told only that there was garbage, grew past what the
  machine had: about one case in 800 ended the program, and each passed
  alone. The VM is now collected every 20 cases.
- **Three tests compile 65,536 regular expressions** through `eval` each,
  and in 512 MB the engine ran out. The guests have a gigabyte, which the
  machines JetSki is for have many times over.
- **And a program that dies still says nothing** (the roadmap's *last
  words*): every one of these ended with code 70 and no sentence, and was
  found by what the tests around it did.

## Not yet decided

Nothing W4 waits on. Two things later steps will ask:

1. **The JIT.** The LLInt is an interpreter, and a page heavy with script
   is several times slower in it. A JIT wants a page writable and then
   executable, which W2 built at two addresses (a region mapped writable
   at one and executable at the other) - so the JIT is a later step and
   Diego's, after W4 says how slow the LLInt is here.
2. **The ARM build**, when ARM's tests resume.
