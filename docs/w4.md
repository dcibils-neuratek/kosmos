# W4 - JavaScriptCore on Kosmos

*Planned 11 November 2026, the day W3 was finished. Its source fetched,
not committed - Diego's choice the same day.*

JetSki's step W4 (`docs/webkit.md`): `jsc`, JavaScriptCore's shell, built
for Kosmos with the LLInt - its interpreter - and no JIT, running a
script; then test262's language tests counted, and the count kept as a
regression. The first time anything of WebKit runs here.

**In short.** Five parts, each leaving a test. The C++ runtimes again,
with threads, on the POSIX layer; ICU, which WTF and JavaScriptCore
include from their first file; WTF and bmalloc; JavaScriptCore and `jsc`
in an image of their own; and test262.

---

## Where the source comes from

**Fetched, not committed** (README's decision log, 11 November). Each
release tarball goes into `build/downloads/`, is held to its published
SHA-256 before anything reads it, and is unpacked under `build/`. What
the tree carries is Kosmos's: the toolchain file, the CMake cache of
options, the port's few source files, and patches as files the build
applies - a patch is a build step somebody can read, as `lua/patches/`
is for Lua.

- **WebKitGTK 2.54.2** (23 October 2026), 47.7 MB, SHA-256
  `a76345b391bef6211fb5ab6cfab2e86b285d18cda17cbb9ade595f1252b86065`, from
  `webkitgtk.org/releases/`, its sum from the `.sums` file beside it. The
  GTK release tarball rather than WebKit's repository: it is WebKit's code
  at a release, it carries `OptionsJSCOnly.cmake` - the JSC-only port,
  the one to follow - and it is 48 MB where a clone is tens of GB.
- **ICU 79.1** (22 October 2026), `icu4c-79.1-sources.tgz`, 28.2 MB,
  SHA-256 `06fa63ecb521048f8082f12ad988f6b678d90cbd88aafce24cbc94902b191d99`,
  GitHub's digest for the release asset; and `icu4c-79.1-data-bin-l.zip`,

  `72489fb316a60ae1c1da205866edd01b17e8fbf8354ad0615e6cc60f74e08811`.

## The port, in one paragraph

**JSCOnly, the Generic event loop, static.** WebKit has a port that
builds JavaScriptCore and nothing else (`OptionsJSCOnly.cmake`), and its
event loop needs no GLib - a `RunLoop` on WTF's own threads and timers.
Built static (`ENABLE_STATIC_JSC`), so it links into an image as every
kit here does, and with the JIT off (`ENABLE_JIT=OFF`, the LLInt and the
C loop's fallback where the offline assembler has no backend), so nothing
the process writes is ever run: the JIT's two mappings of one region,
which W2 built, wait for the JIT's own step (below). A Kosmos `OptionsKosmos.cmake` is not needed at
first: JSCOnly with the Kosmos toolchain file and a cache of options, as
the runtimes are built (`runtime/cxx/`).

## W4a - the C++ runtimes, with threads

libc++ was built with threads, the monotonic clock and the random device
off (`runtime/cxx/runtimes.cmake`), because there was nothing to build
them on. W3 built it: pthreads, `clock_gettime`, `getentropy`. ICU and
WTF use `std::mutex`, `std::condition_variable` and `std::atomic`, and
libc++abi's guard for a function's statics wants a lock. So the runtimes
are configured again with threads on, against the POSIX layer's headers,
and the images that link them link the layer too. *Test*: `cxxtest.elf`
gains `std::thread`, a `std::mutex` held by two, and a static initialised
once by two threads racing for it.

## W4b - ICU

ICU 4C's `common` and `i18n`, compiled by clang with the toolchain file
into `libicuuc.a` and `libicui18n.a` - by a list the build keeps rather
than ICU's `configure`, which cannot run a Kosmos program to learn about
one, as FFmpeg's could not (`tools/ffmpeg_vendor.py`). The data is the
prebuilt little-endian `icudt79l.dat`, linked into the image that needs it
and handed to ICU with `udata_setCommonData` before anything asks, so no
file is opened for it; trimmed later with ICU's data filter when its size
is worth the work. *Test*: an image that normalises, collates, breaks a
sentence into words and formats a number in two locales, each against
the answer ICU gives on this Mac.

## W4c - WTF and bmalloc

The first of WebKit: WTF and bmalloc (and libpas inside it) through
CMake, JSCOnly, static. Where WTF asks for something the POSIX layer
does not have, the layer grows it, or WTF's Kosmos file says what to do
instead - `fork` and signals never. *Test*: WTF's own `RunLoop` and a
`WTF::Thread` started, a `HashMap` and a `String` doing their work.

## W4d - JavaScriptCore and `jsc`

JavaScriptCore with the LLInt, and `jsc` linked into `jsc.elf` - an
application installed in `/Home/Apps/JSC` as Doom is, its image with the
engine, ICU and its data. The offline assembler is Ruby, run on the host
during the build (`/usr/bin/ruby`). *Test*: `jsc` running a script that
exercises the language - closures, classes, generators, `async`, a
`Proxy`, a regular expression, `Intl` - and printing what it computed.

## W4e - test262

test262's language tests, fetched at a tagged commit as the rest is, run
by `jsc` in the guest and counted: passes, failures, and which. The count
is kept as a regression, as `bench/baselines.json` keeps the
benchmarks' - a run that passes fewer than the last is a failure.

## Not yet decided

Nothing W4 waits on. Two things later steps will ask:

1. **The JIT.** The LLInt is an interpreter, and a page heavy with script
   is several times slower in it. A JIT wants a page writable and then
   executable, which W2 built at two addresses (a region mapped writable
   at one and executable at the other) - so the JIT is a later step and
   Diego's, after W4 says how slow the LLInt is here.
2. **The ARM build**, when ARM's tests resume.
