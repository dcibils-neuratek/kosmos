# musl's maths, vendored

Thirty-two files from **musl 1.2.5**, unmodified, under musl's own MIT
licence — the text is in `COPYRIGHT` beside them, exactly as shipped.

    source   https://musl.libc.org/releases/musl-1.2.5.tar.gz
    sha256   a9a118bbe84d8764da0ea0d28b3ab3fae8477fc7e4085d90102b8596fc7c75e4

## Why this is here

Kosmos needs thirteen functions it has no business writing: `sin`, `cos`,
`sqrt`, `pow`, `fmod`, `acos`, `asin`, `atan2`, `tan`, `log`, `log2`,
`log10`, `exp`. `runtime/libc/math.c` has the other half — `fabs`, `trunc`,
`floor`, `ceil`, `frexp`, `ldexp` — which is bit manipulation and is
exactly the sort of thing this project exists to understand. A correct
`pow` is numerical analysis, and `runtime/include/math.h` records where the
line was drawn.

**They used to come from newlib, and that was a dependency nobody decided
on.** It worked because ARM's official GNU toolchain happens to ship newlib
beside the compiler. Homebrew's `x86_64-elf-gcc` ships `libgcc.a` and
nothing else, and there is no `x86_64-elf-newlib` to install — so the second
architecture found that this system's userland had been linking a libc it
does not use and does not want. `<inttypes.h>` was the same discovery a day
earlier: not a freestanding header, taken from the same place, and now in
`runtime/include/`.

Vendoring makes both machines compute `sin` with the same code, which
matters for a system whose whole point is that the same Lua runs on both.

## What was taken, and how the list was arrived at

Not by judgement. Every file in `src/math` was compiled, the thirteen
wanted functions were used as a starting set, and the closure was taken over
undefined symbols until nothing was left unresolved — which is where the
number 32 comes from and why it is neither round nor negotiable. Five of
them are data tables (`exp_data.c` and friends) that no function name
points at, so the closure follows *symbols* rather than names.

The `long double` variants, the `float` variants, the Bessel and gamma
functions and everything else musl has are not here. They compile, and
nothing asks for them.

**Two files the closure named are deliberately not here either**: `fabs.c`
and `floor.c`. `runtime/libc/math.c` already implements both, and its
header says why that half is ours — it is pure IEEE-754 bit manipulation,
about 150 lines, and exactly the sort of thing this project exists to
understand. Musl's sources call them and the linker resolves them against
ours, which is the arrangement that was always intended.

## How it builds

Nothing here is modified, so two things are supplied from outside:

- `-Dhidden= -Dweak=`, which musl's own build injects through a generated
  `vis.h`. They are ELF visibility attributes for a shared library; this
  system links one static binary and has no use for either.
- `runtime/include/` comes *first* on the include path, so musl's sources
  compile against this system's `math.h`, `stdint.h` and `endian.h` rather
  than musl's. `include/features.h` here is musl's own and is the one
  header of theirs that is genuinely needed; adding the whole of musl's
  `include/` would shadow the compiler's `stdint.h` with one that wants a
  `bits/alltypes.h` generated by musl's configure.

`arch/aarch64/fp_arch.h` and `arch/generic/fp_arch.h` are musl's, and the
build puts the architecture's directory before the generic one — so AArch64
gets its own and x86-64 falls through to the empty generic one, which is
what musl does.
