# assets/images

PNGs carried inside the system image and served to applications by name.

There is no disk until M8, so a picture reaches a running Kosmos the same way
a program does: it is compiled in. Drop a `.png` here, run `make`, and it is
available to any application as `sys.asset("name.png")`.

`test-pattern.png` is generated by `tools/mkpattern.py` and is deliberately
awkward: it is RGBA rather than RGB, and it uses **all five** PNG row filters
in rotation. A decoder that only handles the "none" filter, or that assumes
three channels, fails on it at once rather than on somebody's photograph a
month later.

`test-quads.jpg` is the same idea for the other decoder, and it is shaped by
what JPEG is: four solid 64x64 quadrants - red, green, blue, near-white - so
that a lossy codec still lands within a few units of the right colour at the
centre of each one. The test pattern above would be a poor JPEG fixture for
exactly the reason it is a good PNG one: its whole point is per-row filters
and an alpha channel, and JPEG has neither.

It is a committed file rather than a generated one, deliberately. A decoder's
regression test wants bytes that never move: a fixture regenerated by the
build could start failing because the *encoder* on this machine changed,
which is a day spent on the wrong question. The image it was made from is
128x128 with those four quadrants, and it is 1,125 bytes.

Anything else here is whatever you put here, and it is yours; the generated
pattern and the quads are the project's.

**Size matters more than usual.** These bytes are in the kernel image and
in RAM for the whole run, and decoding one costs its pixels twice over -
once for the inflated rows and once for the surface. A 1280x853 photograph
is about four and a half megabytes of surface. That is affordable and it is
not free, and it is the reason M8's filesystem exists.
